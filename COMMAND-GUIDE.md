# DT Init commands: what each one is for

One row per slash command, current with release 5.4.0 (29 commands, 8 roles). Type the command in Claude Code. Commands marked user-only (`composio`, `dpp-full`, `fullauto`, `knowledge`, `machine-prep`, `model`, `onboard`, `sdk`) never start on their own. New in 5.1: `/dt-init:pr-sweep`, provider profiles, per-provider rules, API-key providers, env isolation, speed defaults (note under the table).

## For people

Scan the table for the job you have in mind. "Best for" says when a command is the right pick, and "How to use" gives one example you can type. For every flag, read [docs/COMMANDS.md](docs/COMMANDS.md).

## For agents

- The commands this page marks user-only never start on their own. Run one only when the person typed it.
- This page explains purpose. Take exact syntax from [docs/COMMANDS.md](docs/COMMANDS.md), not from the example column.
- An API-key provider with no rules is read-only. Do not widen a provider's rules yourself. The person does that with `/dt-init:model`.

## Install and update

See [DT Init installation](README.md#for-people).

|---|---|---|---|---|
| **Getting started** | | | | |
| `/dt-init:onboard` | Explains the plugin, its roles and commands, and where to start. Optional Composio yes/no step (see /dt-init:composio); points to API-key providers (see /dt-init:model). Ends with an optional hooks step: lists extra project hooks (command guard, auto-format, tests on stop, notify; db-guard and migration-check for databases) and adds only your picks, after a dry run. | New users could not tell which command fits which job, or how to turn on hooks. | `/dt-init:onboard` | First day with dt; picking commands and hooks. |
| `/dt-init:machine-prep` | Audits this computer's plugins, subagents and skills against the blueprint profile and reports what is enabled, what it costs, and where duplicates exist. Report only — it never changes a setting. | Too many installed tools slow every session. | `/dt-init:machine-prep` | Once per new computer. |
| `/dt-init:composio` | Optional Composio overlap report. Asks once if you have a Composio account and reports which installed plugins, MCP servers and skills a Composio connection would overlap. Report only — it never connects, installs or disables anything, and never reads keys. | Duplicate tools Composio already covers slow startup. | `/dt-init:composio` | Machines that use Composio. |
| `/dt-init:setup` | Interviews you until the goal is written down and approved, then creates the project's .harness files. Works on one repo, many repos or a workspace. Can offer an unattended permission profile (diff first, written only on a yes). | Every later step needs an approved target. | `/dt-init:setup` (add `--scaffold-only` to skip the interview) | Starting any repo or multi-repo workspace. |
| `/dt-init:model` | Picks which AI (Claude, Codex, Gemini) fills the lead, advisory and sign-off seats, and records it as lead_provider. The new lead is given the same skills as Claude, including the current dt plugin, so it can run `/dt` rather than an older `/dts2-harness`. Builders are unaffected. New in 5.1: add or rename a named provider (for example grok-api beside grok; keys kept as a reference only) and edit its rules: allowed tasks, top tier, denied paths, read-only, no secrets, dollar caps. | Teams wanted a choice of lead provider, a second named entry on one provider, and limits on pay-as-you-go providers. | `/dt-init:model` (pick the add/rename or edit-rules option) | Switching the planner or provider; adding an API-key provider. |
| **Everyday work** | | | | |
| `/dt-init:run` | Does one task: plans, builds in parallel, reviews, verifies, ends with a receipt and PR. You approve plan and ship. Can also resume a run, redo one section, add a secret, or review a PR. | The core command, with two human checkpoints. | `/dt-init:run add rate limiting to the API` (also `resume`, `section <#>`, `review-pr <number>`) | Everyday work with you in control. |
| `/dt-init:steer` | Stops and redirects a run in progress: the current step finishes, nothing new starts, it checkpoints a handoff, reviews queued prompts, re-plans and resumes. | Changing direction mid-run meant stopping by hand and losing work. | `/dt-init:steer use the Postgres schema instead` | Changing course mid-run without losing work. |
| `/dt-init:feature` | Plans a new feature: scores clarity, interviews if vague, updates plan docs, opens a plan PR. Builds nothing. | Roadmap docs drifted apart. | `/dt-init:feature "nightly report email"` | Adding to the roadmap before building. |
| `/dt-init:ship` | Turns your branch into a checked pull request (checks, secret scan, verifier and reviewer, receipt), then offers to clean stale branches after your yes. Never merges. | Hand-made branches skipped checks and secret scans. | `/dt-init:ship dev` | Finishing work you built by hand. |
| `/dt-init:gtm` | One go-to-market pass: uses marketing skills when already installed, ends with a launch-readiness scorecard. | Launch checks were scattered. | `/dt-init:gtm` | Before launching a product or site. |
| **Unattended and parallel runs** | | | | |
| `/dt-init:autopilot` | Runs chosen steps with no human checkpoints; a three-provider gate and a council replace them. One branch and PR per step. New in 5.1: no more than 5 of its PRs stay open (open_pr_cap); it runs /dt-init:pr-sweep when the pile reaches the cap. | Approvals blocked unattended work. | `/dt-init:autopilot 3-5` (also `resume`, `status`) | Well-defined steps you trust to run alone. |
| `/dt-init:dpp` | A head session runs several autopilot lanes in parallel as background workers, merges in order, writes one report. | Autopilot did one step at a time. | `/dt-init:dpp dry-run` (also `--full`, `resume`) | Many independent items; dry-run previews. |
| `/dt-init:dpp-full` | dpp where the head also fills lanes from a delegation scan and keeps dispatching (user-only). | dpp needed approval per batch. | `/dt-init:dpp-full` | A big backlog with less supervision. |
| `/dt-init:fullauto` | dpp-full with autopilot forced on, looping check-in until nothing is outstanding (user-only). A loop guard stops it on a STOP file, a stall or a spent budget. | To finish a whole end state unattended. | `/dt-init:fullauto` | Whole backlog overnight, within budget caps. |
| `/dt-init:cooldown` | Pauses a provider that hit a usage limit until its reset date; `clear` resumes it, `list` shows who is paused. One status file (~/.dts2/agent-status.json) is shared by every session on the machine; paused providers return on their own. | Sessions kept calling an exhausted provider. | `/dt-init:cooldown set codex 2d` (also `clear codex`, `list`) | Keeping runs going when a provider is out of usage. |
| **Status and memory** | | | | |
| `/dt-init:check-in` | Read-only checklist of progress against the goal: N of M done, plus open action items. `all` reports the check-in items of every session on this computer in one list and, after your yes, asks them for fresh ones. | One quick answer to "where are we?", for one session or all of them. | `/dt-init:check-in` or `/dt-init:check-in all --since 24h` | Status at any time; `all` when many sessions run. |
| `/dt-init:go` | Reads the repo and runs the next command it needs, on a fixed ladder from setup to complete, then repeats. A script picks the route. It stops at the roadmap approval, at a stop file, and whenever a person is needed. | When you do not know which command comes next, or want one command to carry a repo forward. | `/dt-init:go`, `/dt-init:go status`, `/dt-init:go stop <reason>` | Any repo, at any stage. |
| `/dt-init:action-items` | Lists what needs a person (secrets, decisions, handoffs, deploys, promotions); mark done, add or assign. | Runs stalled silently on human-only tasks. | `/dt-init:action-items done S1` | "What is blocked on me?" |
| `/dt-init:fleet` | Lists every dt session on this computer with status, repo and last activity, and shows any one's logs and ledgers read-only. Broadcasts a note, knowledge, handoff, pause or check-in request to all sessions (or by repo, label or id) at once, after confirming how many it will reach. | No way to see or message ~30 terminal sessions without going tab by tab. | `/dt-init:fleet` to list, `/dt-init:fleet broadcast --kind handoff --text "update coming"` | Many parallel sessions. Idle ones see a message at their next prompt, tool call or stop. |
| `/dt-init:incidents` | Shows role incidents that hooks record automatically (thin brief, partial report, one role redoing another's files, a hung spawn, API errors), the roles running now, and an end-of-run brief. `review` sends open incidents to one read-only reviewer that finds root causes, queues lessons and promotes repeat trends (project, this computer, knowledge store, plugin PR only on your yes). | Roles misfired or hung with no record; mistakes repeated. | `/dt-init:incidents live`, `/dt-init:incidents list --open`, `/dt-init:incidents review` | After a run, or when sessions seem stuck. Off: `incident_capture: false`. |
| `/dt-init:learn` | Turns reviewer findings into lasting per-repo lessons that later runs read. Prunes stale ones only after you approve. | The same mistakes kept recurring. | `/dt-init:learn promote L-012` | After runs; improving quality. |
| `/dt-init:loop` | Researches one role instruction on a frozen batch of past-month receipts, with fixed token and time caps and one metric. It keeps or reverts each change mechanically, logs every attempt, and sends kept changes out through ship. | Role-instruction tuning had no measured, bounded loop. | `/dt-init:loop <experiment.json>` | Improving a role's instructions with evidence. |
| `/dt-init:knowledge` | Your personal store of preferences, terms and learnings, shared across all your devices (user-only). Read only when you invoke it or during /dt-init:setup. Never stores secrets. | Defaults and terms were stuck in one repo or head. | `/dt-init:knowledge setup` (once per person), `join` (per new device), then `set` / `get` / `find` / `list` / `rm` / `sync` / `status` | Store: private GitHub repo, Cloudflare or synced folder. |
| **Maintenance** | | | | |
| `/dt-init:find-skills` | Rescans the repo, asks 1-3 questions, then ranks up to 12 improvements (skills, database tooling, hooks, MCP servers, plugins, commands, subagents, permissions, CI, docs). Wires in only your picks. | Databases and hooks were left out of skill-only scans. | `/dt-init:find-skills` | When the project changes or uses a database (Prisma, Supabase, SQLite). |
| `/dt-init:ask-expert` | Reviews one repo: pins down your goal, compares what you think it is with its code and your active repos, then a 3-provider panel votes KEEP, FOLD, TEMPLATE, ARCHIVE or DELETE (the council decides after three failed rounds). Ends with a one-page memo, salvage list and 0-100 scorecard. Changes nothing. | No way to tell which old repos were worth keeping. | `/dt-init:ask-expert my-old-app "keep or sell?"` | Deciding one repo's fate. |
| `/dt-init:repo-sweep` | Batch version: a quick ask-expert pass on every repo of an owner, oldest first, then one cleanup screen sorted by score. Archive is reversible; delete is never bulk and needs the typed repo name and a backup bundle. | One-by-one cleanup took too long. | `/dt-init:repo-sweep Dobeu-tech-eco` | Clearing out many old repos. |
| `/dt-init:pr-sweep` | New in 5.1. Clears open and stale PRs in one pass with parallel workers: buckets every PR, merges green ones (merge commits only), rebases, triages red CI, closes dead or superseded ones with a comment, and lists what waits on you. Never bypasses branch protection. `--optimise-ci` adds a CI-speed PR. | Autopilot runs left piles of open and stale PRs. | `/dt-init:pr-sweep` or `/dt-init:pr-sweep owner/repo --stale-days 5 --mine` (also `--optimise-ci`) | After an autopilot run, or when PRs pile up. |
| `/dt-init:evolve` | Changes the plugin at its source repo: edit, validate, test, bump the version, commit; pushes only on your yes. | Harness lessons needed a safe route into the plugin. | `/dt-init:evolve` (or `/dt-init:evolve deploy`) | Maintainers only, not normal projects. |

**Providers and rules (5.1).** Provider profiles can be built in, per user (`~/.dts2/agents`) or per project (`.harness/agents`), and any provider can have your own name: `roster.py list`, `add`, `rename OLD NEW`, `suggest-name` (or use `/dt-init:model`). Three built-in API-key providers run on a pay-as-you-go key, billed apart from subscriptions: `claude-api`, `codex-api`, `grok-api`. They review, give second opinions and (claude-api only if you widen its rules) build overflow; they never lead or sign off. Keys are stored as a reference only (keyring, 1Password, Doppler or an env var), never in the repo. An API-key provider with no rules is read-only (review, docs, research), at most standard tier, $0.50 a run and $5 a day, and can never deploy, merge, release, touch secrets or delete. Change rules with `/dt-init:model` or `roster.py rules <name> --show`, `--set key=value`, `--reset`. Details: docs/API-AGENTS.md.

**Env isolation and speed (5.1).** Subscription providers and sons run with every API-key variable removed, so a stray key in your shell cannot bill the API account. Sons, verifier and fixer default to Sonnet (`son_model: opus` for hard tasks); fix rounds 4-5 go to a fresh Opus worker.

**Prompt intake (automatic, no command).** A UserPromptSubmit hook (`prompt-intake.sh`) queues every prompt you type while the harness works (`.harness/intake.jsonl`, shown in `.harness/intake.md`), scores its clarity and folds clear ones into the run; unclear ones get at most two short questions at a safe point. It never blocks (off: `intake: false` in `.claude/dts2-harness.local.md`). Only `/dt-init:steer` (or a prompt starting `steer:`) stops work. Role incidents are also logged by a hook with no command; review them with `/dt-init:incidents`.
